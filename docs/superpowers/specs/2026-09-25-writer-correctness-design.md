Structural findings that shape the design:

- **Two writer stacks.** Live stack (changes signed output): `has_enough_signature_space` → `realloc_code_sign_space_with_metadata` (writer.rs:877) → `prepare_code_in_place` (writer.rs:1089) → {`update_linkedit_data_command` :464, `add_code_signature_command_with_metadata` :1039, `update_linkedit_segment` :697} → `embed_signature_in_place` (signer.rs:723, out of scope). Goblin-reparse stack (reachable only via uncalled facade `write_signed_macho*` + unit tests): `realloc_code_sign_space`/`_slice` → `_single`; `prepare_code_for_signing`/`_slice` → `prepare_code_single`; `embed_signature` → `embed_signature_single`. Fixes must land in **both** stacks (same files, both are public API).
- **`LC_CODE_SIGNATURE.dataoff` divergence:** 4 sites write raw `code_length` (writer.rs:164, 200, 916, 954 — both realloc variants); 8+ sites write `align_to(code_length, 16)` (embed/prepare paths: 395→411/419, 832→841/849, 1008→1017/1025, 1101→1108/1113). Apple and LIEF both align the signature start to 16 (librarian Q5).
- **Guard divergence:** `add_code_signature_command` (writer.rs:496) and `inject_dylib_command` (writer.rs:621) hard-error when `insert_end > first_segment_offset`; the two realloc variants instead do a `sizeofcmds`-based slack subtraction (writer.rs:173-183 / 930-939) that (a) measures `bound - (header+sizeofcmds)` (possible `usize` underflow → panic/wrap) while writing at `max_load_cmd_end`, and (b) never checks the output buffer length (inject does, writer.rs:628).
- **Endian:** 4 writer helpers re-sniff `data[0..4]` and silently override `metadata.is_big_endian` (consulted at only writer.rs:893 and :1054). `inject_dylib_command` uses the reference idiom instead: `read_u32(input, 0, false)` then `magic == MH_CIGAM_64` (writer.rs:553-555).
- **Per-slice invariant (must preserve):** parser parses each FAT arch with `MachO::parse(slice_data, 0)` (parser.rs:184) ⇒ all `MachOMetadata` offsets are slice-relative; every live writer call passes per-slice buffers (signer.rs:424/467/557/585). No fix may change that frame or FAT dispatch.
- **Test inventory:** writer tests = exactly 13 (writer.rs:1221-1446), no test anywhere exercises `realloc_*`, `prepare_*`, `embed_signature` success path, or re-signing. Fixtures: `fixtures.rs` has `make_minimal_macho` (`__TEXT` fileoff **0x1000**, not 0; file 0x2000 bytes; no `LC_CODE_SIGNATURE`) + encrypted variant; parser tests hand-roll 3 more builders (one 32-bit no-segment shape drives the 4096 fallback); writer tests use `build_test_binary(segment_fileoff)` (104-byte, `nsects=0`, no `__LINKEDIT`). Missing kinds: fileoff-0-with-sections, big-endian, `vmsize != filesize`, already-signed.

### 1.2 External contracts (scout AppleContracts; sources pinned)

1. **LC append bound is Apple's own rule.** Security `codesign_alloc.cpp:260-296`: before appending `LC_CODE_SIGNATURE`, Apple requires `headerSize + sizeofcmds + sizeof(linkedit_data_command) ≤ firstSectionFileOffset`, where first section comes from the segment with `fileoff==0 && filesize!=0 && nsects!=0`; if no section is found Apple appends anyway (bitcode_strip compat). New LCs are appended at `cmdsEnd` (last position), `cmdsize` multiple of 8, padding zeroed. Kernel rule is weaker (header+sizeofcmds ≤ file, `mach_loader.c:1182`); dyld additionally requires ≤ `__TEXT.filesize` and `__TEXT.fileoff==0` (`MachOAnalyzer.cpp:399-403`). Overwriting section bytes is caught only by stale page hashes (`CS_KILL`, cs_blobs.h:45).
2. **Endian magic layouts — brief item 2 mechanism REFUTED.** On-disk prefixes: BE32 = `FE ED FA CE`, BE64 = `FE ED FA CF`, LE64 = `CF FA ED FE` (loader.h:65/84; goblin 0.10.7 `src/mach/mod.rs:38-46` reads magic BE then `is_lsb = magic == MH_CIGAM || MH_CIGAM_64`; LIEF `enums.inc:4-9` labels `0xFEEDFACE*` the big-endian on-disk forms; dyld `hasMachOBigEndianMagic()` = `MH_CIGAM*`). **Therefore the existing byte-pattern arms `[fe ed fa ce] | [fe ed fa cf] | [ca fe ba be]` DO correctly identify real big-endian files** — the brief's claim that "actual BE Mach-O bytes `ce fa ed fe / cf fa ed fe` fall through" mislabels the little-endian prefixes. Item 2's fix is still executed as briefed (single magic-constant-based detector, `MH_CIGAM`/`MH_CIGAM_64` semantics, parsed context threaded through) plus the demanded end-to-end BE fixture, which becomes the regression lock; the refutation is recorded here and proven by that fixture.
3. **execSegLimit = `__TEXT.filesize`; execSegBase = `__TEXT.fileoff`.** Apple `machorep.cpp:180-227`: `execSegBase` ← `fileoff`, `execSegLimit` ← `filesize` (file-backed extent; never `vmsize`). `cs_blobs.h:243-246` field docs. Our `parser.rs` stores `vmsize` into `text_segment_size` (→ execSegLimit, signer.rs:826) and `vmaddr` into `text_segment_base` (→ execSegBase, signer.rs:825). **The queue item covers execSegLimit only**; `execSegBase`/vmaddr discrepancy is a separate finding recorded in §3 (touching it would break signer.rs test pins = other lane).
4. **Segment filesize vs vmsize:** loader.h:344-349 — `vmsize ≥ filesize`, excess zero-filled; `fileoff+filesize ≤ file size` is a **load-time** `LOAD_BADMACHO` (`mach_loader.c:2290-2294`), so a stale oversized `__LINKEDIT.filesize` after a shrink is a hard failure, not cosmetic.
5. **Signature placement:** LC position among commands is irrelevant to the kernel (dedicated pass, `mach_loader.c:1561-1574`) but appending last is convention; 16-byte `dataoff` alignment is a **tooling** requirement (Apple `(inFileSize + 15) & -16`, LIEF `linkedit_.align(16)`), dyld enforces only pointer alignment.
6. **FAT magics:** `FAT_MAGIC=0xcafebabe` stored big-endian always (fat.h:36-53; kernel accepts BE only). Unchanged by this lane.

## 2. Design decisions per queue item

Each item lists the candidates considered in phase 1 (brainstorm), the pick, and what was rejected. Diffs are described at contract level; exact code lives in the implementation plan.

### Item 1 — insertion bound must see `fileoff==0` content

**Problem.** `find_first_segment_offset` (writer.rs:673-695), `inject_dylib_command`'s inline scan (writer.rs:590-601, 611-612) and parser's `first_segment_offset` (parser.rs:245-256, fallback 294-298) all bound load-command insertion by `min(segment.fileoff where fileoff>0)` or a literal `4096`. The normal linker-produced `__TEXT` has `fileoff==0`, so the real constraint — the first file-backed **section** — is invisible; when `header+sizeofcmds` sits close behind the first section, the 16-byte command write silently clobbers section bytes (no validator catches it; only stale page hashes / `CS_KILL` follow).

**Candidates:**
- **(A) Section-aware bound, fail-closed with `Err` when no content is discoverable.** Bound = min over (sections with `size>0 && offset>0`) ∪ (segments with `fileoff>0 && filesize>0`); `Err` when the set is empty.
- **(B) Section-aware bound, keep a `4096` fallback when the set is empty.** Same bound derivation; empty set → `4096` (today's literal).
- (C) Only tighten the fallback (e.g. derive from `sizeofcmds`) without section scanning. Rejected: cannot see `fileoff==0` content at all — does not fix the bug.

**Pick: (B).** Rationale: (i) it is exactly Apple's append gate (`codesign_alloc.cpp:289`) extended with segment candidates so `test_inject_dylib_command_no_slack` (writer.rs:1423, `build_test_binary(104)` — a sectionless binary whose bound comes from the segment fileoff) keeps working; (ii) the empty set occurs only for synthetic sectionless `fileoff==0` inputs where no content is claimable — Apple itself appends blindly there (`codesign_alloc.cpp:286-288`), and keeping `4096` preserves today's behavior for `build_test_binary(0)` and the parser's 32-bit no-segment fixture (parser.rs:697-723) instead of failing closed on inputs Apple accepts. (A)'s extra strictness buys nothing real (a sectionless `fileoff==0` segment exposes no content to protect) and would churn two existing tests.

**Applied at all three sites + guard unification:**
- `find_first_segment_offset(macho)` (goblin): candidates from `macho.sections` (`size>0 && offset>0`) plus segments (`fileoff>0 && filesize>0`); empty → `4096`.
- `parser.rs parse_single`: same derivation (goblin sections + segments) feeding `MachOMetadata.first_segment_offset` — this is the **live** path (feeds `add_code_signature_command_with_metadata:1048` and `realloc_code_sign_space_with_metadata:930`). Field doc comment updated.
- `inject_dylib_command` byte walk: also walk `section_64`/`section` entries inside each `LC_SEGMENT_64`/`LC_SEGMENT` (offset at LC+72+48 / LC+56+40, size at +40 / +36, validated against `cmdsize`), same union + `4096` fallback (`DEFAULT_FIRST_SEGMENT_OFFSET`).
- **Guard unification** at the insertion points (`add_code_signature_command:491-500`, `add_code_signature_command_with_metadata:1044-1051`, both realloc variants' add-command branches, `inject_dylib_command:617-626`): single addition-only test `insert_end = max(max_load_cmd_end, header_size + sizeofcmds).checked_add(new_cmdsize)`; `Err` if `insert_end > bound` **or** `insert_end > output.len()`. This deletes the `bound - (header+sizeofcmds)` subtraction (removes the `usize`-underflow panic path writer.rs:176/934) and the "measures sizeofcmds but writes at `max_load_cmd_end`" mismatch. No subtraction anywhere ⇒ no underflow by construction.

**Fixtures/tests (fixtures.rs additions):** `make_text_fileoff0_macho()` — realistic two-segment arm64, `__TEXT.fileoff=0` with one `__text` section; tight-gap variant where the section starts 8 bytes after the last load command. Tests: (a) tight-gap → `inject_dylib_command` and the metadata insertion path return `Err` and **section bytes are untouched** (red pre-fix: insertion succeeds and overwrites them); (b) comfortable-gap fileoff-0 injection round trip keeps working; (c) existing `no_slack`/minimal-fixture behavior unchanged.

### Item 2 — big-endian detection consolidated to magic constants + e2e fixture

**Problem (as briefed).** Endian decisions are duplicated five times (writer.rs:140/473/502/701, parser.rs:300) with byte-literal arms, one of which reads `data[0..4]` regardless of slice base, and four of which silently override `metadata.is_big_endian` inside helpers. The brief states the detector misses big-endian files; phase-2 source verification **refutes that mechanism** (§1.2 item 2: `[fe ed fa ce]`/`[fe ed fa cf]` *are* the big-endian on-disk prefixes per loader.h, goblin, LIEF, dyld). No existing test exercises a big-endian Mach-O end-to-end — only `test_read_write_u32_be` (writer.rs:1239, standalone byte helper).

**Candidates:**
- **(A) Single helper keyed on magic constants, called from every site; parsed context (`metadata.is_big_endian`) preferred where available.** Behavior-preserving consolidation (the helper's arm set is algebraically identical: `LE-read magic ∈ {MH_CIGAM, MH_CIGAM_64, FAT_CIGAM}` ⟺ current byte arms) + base-offset-safe bounds in parser + end-to-end BE fixture.
- (B) Thread an `is_big_endian: bool` parameter through every helper (`update_linkedit_*`, `add_code_signature_command*`). Rejected as primary fix: `update_linkedit_segment`/`update_linkedit_data_command` sit on both stacks (4 callers each) and two of their call sites have no metadata object in scope; the parameter would duplicate a value those callers derive from the same bytes — a second convention beside the helper.
- (C) "Fix" only the pattern list (e.g. add `[ce fa ed fe]`). Rejected: those are little-endian prefixes — matching them as big-endian would corrupt the normal case.

**Pick: (A).** One `pub(crate)` helper in `parser.rs` (writer already imports `super::parser::MachOMetadata`, so the import direction has precedent): reads the magic LE at a caller-supplied base with a bounds check and returns `magic == MH_CIGAM || magic == MH_CIGAM_64 || magic == FAT_CIGAM` — exact parity with today's three arms on every input, one source of truth, `base_offset` honored (fixes parser.rs:300's `data.len() >= 4` precondition mismatch). `metadata.is_big_endian` keeps its two reads; all sites now share one derivation instead of re-sniffing divergently.

**Fixture/tests:** `make_minimal_macho_be()` in fixtures.rs — same shape as `make_minimal_macho`, every header/LC field big-endian encoded. E2E test (writer or parser test module): `MachOFile::parse` → `sign_macho_adhoc` → re-parse, asserting (i) `slice.metadata.is_big_endian == true`, (ii) signed output parses and its `LC_CODE_SIGNATURE.dataoff`/`__LINKEDIT` fields decode big-endian (byte-level pin), (iii) the CodeDirectory round-trips through `codesign::verify::parse_superblob` (reachable in-crate; `crate::codesign` is `pub`). **Implementation note:** record the fixture's pre-fix result honestly — per §1.2 detection itself is expected green pre-fix; the test locks the contract the brief demands. If it fails, the root cause is either in this lane's files (fix it) or in `signer.rs`/`verify.rs` (stop that sub-thread and raise one question per the brief).

### Item 3 — realloc must expand from the actually-declared reserve

**Problem.** `realloc_code_sign_space[_with_metadata]` early-returns when `calculate_signature_space(code_length) <= data.len()` (writer.rs:111-115 / 886-890) — a whole-file comparison against a *formula*, blind to what `prepare_code_in_place` already wrote into `LC_CODE_SIGNATURE`. When the declared `dataoff + datasize` exceeds the buffer, the no-op leaves the declaration dangling past EOF and our own parser rejects the output (`parser.rs:268-279`). Deterministic red construction: `code_length=0x6000`, file `0xC000` bytes (old slot `0x6000` ≥ `sig_space+16384=0x5000` ⇒ early return fires), declared `datasize=0x7000` (larger than the `0x6000` old slot ⇒ `dataoff+datasize=0xD000 > 0xC000`).

**Candidates:**
- **(A) `required = max(sig_offset + (calculate_signature_space(code_length) - code_length), checked declared end read from the buffer's own LC)`** (reserve measured from the 16-aligned signature start, so an unaligned-length fresh sign also allocates its pad) **, early-return only if `required <= data.len()`, expansion target = `required`, LC rewritten self-consistently (`dataoff`/`datasize` with checked arithmetic).** Plus a capacity guard where the declaration is made: `prepare_code_in_place`/`prepare_code_with_metadata` refuse (`Err`) when `sig_offset + sig_size > buf.len()` measured **before** truncation, and a `code_length <= data.len()` bounds check makes the truncation total.
- (B) Pass the reserve explicitly (`realloc_code_sign_space_with_metadata(data, metadata, code_length, reserve)`). Rejected: changes the public signature ⇒ forces edits at `signer.rs:424/557` — another lane's file, forbidden by the brief.
- (C) Drop the early return entirely. Rejected: for files with adequate space it would rewrite `__LINKEDIT`/LC needlessly and `resize` could truncate trailing bytes; the early return is correct *when the declared range also fits*.

**Pick: (A).** The declared end is read **from the data buffer** at the known `LC_CODE_SIGNATURE` offset (goblin parse for `_single`, `metadata.code_sig_cmd.0` byte offset for `_with_metadata`) — not from stale metadata — because prepare mutates the buffer and the buffer is what the parser validates. `checked_add`/`checked_u32` on every step (overflow → `Error::MachO`, no panic).

**Why the prepare capacity guard belongs to this item:** the declared range must hold at every observable point. The signer's embed step (`embed_signature_in_place`, signer.rs:723 — out of scope) grows to `max(target, sig_offset + actual_sig)` where `target` is the buffer length captured *before* prepare; therefore `target >= sig_offset + reserve` is exactly the condition for the final file to cover the declaration. Prepare is the only in-scope function that sees both the requested reserve and the pre-truncation buffer, so the invariant becomes a clean `Err` there instead of the current silent past-EOF bytes. Documented behavior change (fail-closed): flows that previously emitted output our own parser rejects now fail with `Error::MachO`; full recovery for those flows needs `signer.rs` to feed the reserve into realloc (§3 residual R1). The guard applies to `prepare_code_in_place` and `prepare_code_with_metadata` only — `prepare_code_single`'s declaration is transient (`embed_signature_single` rewrites the LC from its own signature length and grows its own `Vec`).

### Item 4 — shrink path must re-span `__LINKEDIT` unconditionally

**Problem.** `embed_signature_single` only calls `update_linkedit_segment` when the new signature end *grows* past `linkedit_end` (writer.rs:424-431). Re-signing with a smaller signature leaves `filesize` at its old value while the output shrinks ⇒ `fileoff + filesize > file size` ⇒ load-time `LOAD_BADMACHO` (`mach_loader.c:2290-2294`) and our parser rejects (`parser.rs:281-291`). Additionally `new_filesize` (426) is computed by plain `u64` subtraction *before* the guard (428) — underflow panic in debug builds when `sig_end < seg.fileoff`.

**Candidates:**
- **(A) Unconditional update with checked arithmetic:** compute `sig_end = sig_offset.checked_add(len)`; `new_filesize = sig_end.checked_sub(seg.fileoff)` (Err when the signature ends before `__LINKEDIT` starts — malformed input); call `update_linkedit_segment` unconditionally. `update_linkedit_segment` itself writes `vmsize = max(align_to(new_filesize, 0x4000), original_vmsize)` (writer.rs:708-714): on a shrink the virtual size **never decreases but may grow** to the 16 KiB page-aligned minimum (for the plan's fixture `new_filesize = 0x40` ⇒ `vmsize` goes 0x1000 → 0x4000) — correct per loader.h (`vmsize ≥ filesize`).
- (B) Clamp the output buffer to `linkedit_end` on shrink. Rejected: the buffer length is `sig_offset + signature.len()` by construction (writer.rs:398-405); "clamping" is exactly the unconditional re-span, there is nothing else to shrink.
- (C) Move the condition into `update_linkedit_segment`. Rejected: three `prepare_*` callers already call it unconditionally and correctly (writer.rs:856/1031/1122) — the condition is the bug, and burying a condition inside the helper would change those callers too.

**Pick: (A).** Test: hand-built already-signed fixture (slot 0x800) → `embed_signature` with a 0x40-byte signature → reparse accepted, `__LINKEDIT.filesize == new end`, and `vmsize >= filesize && vmsize >= original 0x1000` (explicitly asserting the never-shrinks invariant; the exact new `vmsize` is `align_to(0x40, 0x4000) = 0x4000`); red pre-fix (reparse `Err`, `linkedit_end > file size`).

### Item 5 — unaligned existing `LC_CODE_SIGNATURE.dataoff`

**Problem (re-anchored).** The `data.len() - code_length` arithmetic is `has_enough_signature_space` (writer.rs:229-232, cited site 1100-1103 refuted — that is `sig_offset = align_to(code_length, 16)` in `prepare_code_in_place`). The full chain: for a re-sign, `code_length` = existing `dataoff`; the signature starts at `align_to(code_length, 16)`; every allocator measures free space from the *unaligned* `code_length`, losing up to 15 bytes; the signer computes `original_sig_space = slice_data.len() - code_length` (signer.rs:462) pad-blind and never grows when its gate passes — so `prepare` declares `sig_offset + slot` up to 15 bytes past EOF and the output fails our own parser. Separately, the two realloc variants write **raw** `code_length` as `dataoff` (writer.rs:164/200/916/954), contradicting the aligned writes of every embed/prepare path.

**Candidates (brief allows either):**
- (i) Reject unaligned existing `dataoff` in the functions that derive `code_length` from it. **Rejected after review round 1 (finding 1):** `prepare_code_in_place` cannot distinguish a pre-existing command from one that `realloc_code_sign_space_with_metadata` just added — the signer passes the original (odd) `slice.code_length` while `working_metadata.code_sig_cmd` is already `Some` in the fresh-sign flow (signer.rs:423-472 vs writer.rs:1112-1117), so any `code_sig_cmd.is_some()`-style guard refuses the valid odd-length **fresh** sign. A correct discriminator would have to inspect pre-realloc state that prepare never sees, or edit `signer.rs` (forbidden).
- **(ii) Subtract the padding everywhere:** every allocation measures from `sig_offset = align_to(code_length, 16)` (item 3's `required` already does), and the item-3 prepare capacity guard turns the remaining pad-blind branch (signer's preserve path, `original_sig_space = len - code_length`) into a clean `Error::MachO` instead of past-EOF bytes.
- (iii) Accept odd offsets silently. Rejected: the preserve branch would still declare past EOF.

**Pick: (ii).** Odd inputs end up in exactly one of two states, both safe: **preserve** (old slot ≥ estimate) → declared end exceeds the untouched buffer by exactly the pad → capacity guard (item 3) refuses before any mutation; **expand** (old slot < estimate) → target `= sig_offset + reserve` allocates the pad, realloc rewrites `dataoff` aligned, output heals to a 16-aligned signature start.
1. Realloc variants: write `dataoff = align_to(code_length, 16)` instead of raw `code_length` (4 sites: writer.rs:164/200/916/954) with `datasize = required - sig_offset`, keeping `dataoff + datasize == target == len`. The expansion *target* is already signature-start-based from item 3 (`required = sig_offset + reserve ∧ max declared end`), so this task only lands the aligned writes. For aligned inputs (every existing fixture) values are byte-identical to today.
2. `prepare_code_in_place` / `prepare_code_with_metadata` keep no alignment special-case — the capacity guard added in item 3 is the enforcement point (it necessarily fires for odd preserve, since `sig_offset + slot = len + pad > len`).

Apple's tooling contract backs the pick: 16-byte `dataoff` alignment is what `codesign_alloc.cpp:299` and LIEF `Builder.tcc:1003-1006` write; dyld only demands pointer alignment, so allocating the pad and rewriting `dataoff` aligned is safe — and because the signer's slot math (`original_sig_space = len - code_length`, signer.rs:462) stays pad-blind, enforcing the pad at the writer boundary (capacity guard + aligned target) is the only in-scope place it can be enforced.

**Tests:** (a) direct prepare on an odd-`dataoff` signed slice whose slot does not cover the pad → `Err` from the capacity guard (red pre-fix: silently declares past EOF); (b) e2e odd re-sign through `sign_macho_adhoc` → succeeds and the output reparses with a 16-aligned `dataoff` (red at base: `Ok` whose output our parser rejects; contract lock from task 3 on); (c) fresh sign of an unaligned-length file → `dataoff` 16-aligned, `dataoff + datasize <= len`, output reparses (red at base for the `+15` overshoot; lock from task 3 on); (d) direct realloc with odd `code_length` → output `LC_CODE_SIGNATURE.dataoff` aligned and `dataoff + datasize == out.len()` (**the task-5 red test**: realloc writes raw `code_length` until this item lands); (e) aligned re-sign unaffected (existing signer/verify round trips stay green).

### Item 6 — `execSegLimit` must be the file-backed extent

**Problem.** `parse_single` stores `__TEXT.vmsize` into `ArchSlice.text_segment_size` (parser.rs:237-240 / 250-253); the signer writes it as CodeDirectory `execSegLimit` (signer.rs:826 → `code_directory.rs:382`). Apple writes `__TEXT.filesize` there (`machorep.cpp:205-227`), `vmsize` including zero-fill being wrong. Consumer map (scout CallerMap): the *only* consumers of `text_segment_size` are signer.rs:826 (execSegLimit), the two pass-through copies (signer.rs:441/573) and two pinning tests whose fixtures have `vmsize == filesize` (signer.rs:1068, :1400-1403) — so no separate `vmsize` field is needed.

**Candidates:**
- **(A) Store `seg.filesize` into `text_segment_size`; update the doc comment (parser.rs:110-111) to say file-backed extent; no new field.**
- (B) Add `text_segment_filesize` alongside, keep `vmsize`. Rejected: no consumer exists (YAGNI), and a second field invites choosing the wrong one.
